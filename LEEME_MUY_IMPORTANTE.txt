 PASO 0 — LO MÁS IMPORTANTE: FALTAN LAS CREDENCIALES DE CLOUDINARY
════════════════════════════════════════════════════════════════════
Revisé su .env actual y confirmo que las variables CLOUDINARY_CLOUD_
NAME, CLOUDINARY_API_KEY y CLOUDINARY_API_SECRET todavía NO están
puestas — el código ya las lee (con dotenv/process.env), pero sin
ellas ninguna subida de archivos va a funcionar.

Para obtenerlas:
  1. Cree una cuenta gratuita en https://cloudinary.com (el plan
     gratuito alcanza sobradamente para esto).
  2. En su Dashboard aparecen de una vez: "Cloud Name", "API Key" y
     "API Secret".
  3. Agregue estas 3 líneas a su archivo .env (en el mismo lugar
     donde está DATABASE_URL):
        CLOUDINARY_CLOUD_NAME=su_cloud_name
        CLOUDINARY_API_KEY=su_api_key
        CLOUDINARY_API_SECRET=su_api_secret
  4. En Render (producción), agregue las mismas 3 variables en la
     sección "Environment" del servicio.

════════════════════════════════════════════════════════════════════
 PASO 4 — MIGRAR LOS DATOS EXISTENTES A UNA BASE NUEVA Y LIMPIA
════════════════════════════════════════════════════════════════════
Este paso es OPCIONAL pero es el que de verdad resuelve el consumo
alto de "Network Transfer" en Neon: mueve TODOS los datos actuales
(usuarios, instituciones, estudiantes, notas de los 4 periodos, todo)
a una base de datos NUEVA, subiendo de paso cualquier Base64 que
siga existiendo de antes de esta corrección.

  1. En Neon, cree un proyecto/base de datos NUEVO (vacío). Copie su
     cadena de conexión.
  2. En su .env, agregue una línea NUEVA (sin borrar DATABASE_URL,
     que debe seguir apuntando a la base ACTUAL):
        NEW_DATABASE_URL=postgresql://.....(la cadena de la base nueva)
  3. Confirme que las 3 variables de Cloudinary (Paso 0) también
     estén puestas — si no, el script migrará los datos pero no
     podrá limpiar las imágenes en Base64 que encuentre.
  4. Ejecute:
        npm run migrate-db
  5. Lea el resumen que imprime al final: cuántos registros copió,
     cuántos archivos subió a Cloudinary, y si hubo algún error (si
     algún archivo falla al subir, NO se pierde — queda en Base64 en
     la base nueva, y el script se lo señala para que lo revise).
  6. Es seguro correrlo más de una vez — no duplica datos, actualiza
     lo que ya existía.
  7. SOLO cuando esté conforme con el resultado (revise la base
     nueva directamente si quiere estar seguro), cambie DATABASE_URL
     en su .env para que apunte a la base NUEVA, y reinicie el
     servidor. En Render, actualice la variable DATABASE_URL ahí
     también.

IMPORTANTE: el script NUNCA modifica ni borra la base de datos
ACTUAL — solo LEE de ahí. Su base actual queda intacta como respaldo
natural, incluso después de migrar.
